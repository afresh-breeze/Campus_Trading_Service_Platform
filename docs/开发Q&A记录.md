# 开发 Q&A 记录

---

## 1. `users.status` 用状态控制禁用，而不是物理删除用户，这样设计有什么用？

物理删除在这个库里根本走不通。`items.seller_id`、`errand_orders.publisher_id`、`conversations.user_a_id/user_b_id`、`messages.sender_id` 都是 `ON DELETE RESTRICT`，一个发过商品、接过单、聊过天的用户，`DELETE` 会直接被数据库以 1451 错误拒绝。所以 `status` 是这套外键体系下唯一可行的注销出口。

它同时解决了四件事：一是保住交易凭证，订单、聊天、状态日志是纠纷追溯的唯一依据，人走了记录还在；二是堵住删号重注册的漏洞，`student_no` 是唯一键，行被删掉学号就释放了，同一个人可以换回一个 `credit_score = 60` 的干净账号，保留行则学号一直被占用；三是可逆，误操作只需一条 `UPDATE` 就能恢复；四是用 `ENUM('active','disabled')` 而非布尔值，以后加"临时冻结""待审核"只是加枚举值。

字段本身不会自动生效，代码要配合三处：登录在校验密码后再查 `status`，`disabled` 返回 403 而不发 token；JWT 无状态，要在鉴权中间件每次回查，否则旧 token 仍可用；查询展示时要想清楚要不要过滤，找跑腿列表只出 `active`，历史订单里的用户名则不能过滤。

## 2. 真实业务中，软删除的数据不会越积越多吗？

会，但真正撑爆表的通常不是 `users` 这类主数据，而是聊天和日志这种流水数据。`users` 的规模由学校人数封顶，两万行不过几 MB，十年不清也无所谓；`messages` 才是失控点——日活 5000、人均 20 条，一年就是几千万条、十几 GB。

业界的处理路径是热冷分层加匿名化替代删除：主库只留近一年，更早的数据归档到历史库或对象存储；到期后不删 `users` 行，而是清空手机号、头像，昵称改成"已注销用户"，让行变成一行没有信息量的壳，外键依然有效、订单仍能显示"已注销用户"；大表按 `created_at` 分区，过保留期用 `DROP PARTITION` 秒级清理，而不是逐行 `DELETE`；清理必须分批 `DELETE ... LIMIT 1000` 循环，一次删几百万行会持有超长事务、撑爆 undo log 并造成主从延迟。

软删除自身还有三个麻烦：唯一键被占用（学号无法释放）、索引碎片（`DELETE` 只打标记，空间进空闲列表但表文件不会缩小）、低选择性列加索引收益差（`status` 只有两个值，要放进复合索引前缀才有意义，且当前缀的值分布一旦倾斜就失效）。

对课程项目而言这套治理完全不必实现，但答辩时能说清"逻辑删除的代价在哪里"是加分项。你这套表把主数据和流水数据分开存放，将来真要归档只需对流水表动手，这已经为分别治理留好了边界。

## 3. `books.price_ref` 只是参考价，不参与实际交易，那它存在的意义是什么？

它存的是这本书的官方定价，是书本身的公共属性，不随卖家变。作用有两个：一是给不知道该卖多少钱的卖家一个定价锚点，发布页可以提示"定价 59，本校二手成交均价 18，建议 15~25"；二是给买家一个折扣参照，详情页"定价 59 / 售价 15 / 2.5 折"比孤零零一个"¥15"信息量大得多。

它必须放在 `books` 而不是 `items`：同一本书有二十个卖家，定价塞进 `items` 就是二十份副本，出版社调价或录错一位就要改二十行且无法判断哪份是对的。拆到 `books` 之后定价只存一份，所有引用 `book_id` 的商品共享，这也正是 3NF 的要求——`price_ref` 只依赖 `book_id`，放进 `items` 就成了传递依赖。

要区分的是它和 `items.original_price` 的口径：`price_ref` 是客观的官方定价，`original_price` 是卖家自己声称的购入价，可能是原价买的也可能是打折买的。同一本定价 59 的书，两个卖家都卖 15，一个填 59、一个填 40，折扣看起来完全不同。所以前端标签不能互换，"定价"和"原价"是两个词。

`price_ref` 不参与任何业务规则，既不进 `WHERE` 也不进 `ORDER BY`，纯粹是给人看和给统计看的展示字段。它允许为空，是因为手动录入、没查到 ISBN 的书可能根本不知道定价，附录 A 的 `CHECK (price_ref IS NULL OR price_ref >= 0)` 显式写出 `IS NULL`，虽然与 `>= 0` 效果相同（CHECK 遇 NULL 返回 UNKNOWN 且视为通过），但能表明作者是有意处理了 NULL 的情况。

## 4. `items.original_price` 又是用来干什么的？

它是卖家自己填的"我当初买它花了多少"，唯一作用是给买家一个"省了多少"的对照，比如"¥25，原价 ¥199，省 87%"。这个字段不参与任何查询、排序或校验，纯粹是展示。

它和 `price_ref` 的差别在"谁说的"：`price_ref` 是系统导入的客观定价，全站统一；`original_price` 是卖家主观声明，无法验证。同一本书有人原价买、有人双十一 40 拿、有人从学长手里 20 收，都卖 15 时填的 `original_price` 各不相同，折扣也从 2.5 折到 7.5 折不等。它记录的不是物品属性，而是卖家的个人叙事。

真实业务里这个字段是有监管风险的，《明码标价和禁止价格欺诈规定》明确禁止虚构原价，而卖家填多少都零成本，结果就是划线价集体注水、买家不再相信。

你这版 DDL 只写了 `CHECK (original_price IS NULL OR original_price >= 0)`，只保证非负，没保证原价不低于售价，于是 `price = 50 / original_price = 30` 也能入库，前端会渲染出负数折扣。建议补一条 `CHECK (original_price IS NULL OR original_price >= price)`，这是个很好的答辩素材——主动承认一条缺失的约束，比被问出来强。

课程项目里三个选择：保留但只当展示字段、前端标清"卖家所述原价"最省事；砍掉用 `price_ref` 顶替最干净，代价是非书籍商品失去折扣表达；保留并加约束最完整，但要回答"怎么判断离谱"。

## 5. `item_id` 上的外键为什么会自动创建索引？

InnoDB 强制要求外键列所在的子表上有以该列为**最左前缀**的索引，因为约束执行要双向查：插入子表时确认父表存在（走父表主键，很快），删除父表时必须反查子表有无引用（走子表的外键列）。后者若无索引就退化为全表扫描——`favorites` 五百万行，只为删三条收藏就要扫全表，批量删除时更是 O(N × 子表行数)。

`favorites` 的主键是 `(user_id, item_id)`，这是一棵按 `user_id` 排序、同 `user_id` 内再按 `item_id` 排序的 B+ 树。`user_id` 是第一列，`fk_favorites_user` 直接借用，不新建；`item_id` 是第二列，跨用户完全乱序，无法按它二分定位，所以 MySQL 判定"不可用"，自动补建一个单列索引，名字默认沿用约束名，于是 `SHOW CREATE TABLE` 里会多出一行你 DDL 里没写的 `KEY fk_favorites_item (item_id)`。

三个副作用要知道：删外键不会删索引，`DROP FOREIGN KEY` 之后那个索引会留下来白白增加写成本，必须再 `DROP INDEX`；索引名在表内唯一，手写同名索引再加同名约束会报 1061；父表被引用列也必须建索引，否则报 1822。

这个索引并非纯负担，它同时支撑"谁收藏了这个商品"这类反查，以及 `COUNT(*) WHERE item_id = ?` 式的收藏数统计。答辩可以按三步答：强制规则 → 复合主键不满足最左前缀 → 顺带支撑业务查询。

## 6. 发布者都还没说要取什么，跑腿怎么报价？`base_price` 这样设计合理吗？

如果把它理解成"针对某一单的报价"，确实不合理；但它的真实语义是"起步价"——我愿意接单的最低档位，就像搬家师傅说"起步 100"，他也不知道你家有几件家具。

前提是这个平台单边定价：`errand_orders.reward` 由发布者填写且 `NOT NULL`，发单即定价，跑腿只能选接或不接，没有应价、竞价的表或字段。所以"跑腿对具体订单报价"这件事在系统里根本不存在，`base_price` 不属于交易链路，而是挂在 `runner_profiles` 上的静态自我介绍。

它真正的价值是缓解发布者的定价困境。文档 3.6 节找跑腿的 SQL 会把这个字段查出来，发布者发单前预览，看到匹配到的几个人起步价分别是 5、6、8 元，而自己准备填 3，立刻就明白这单大概没人接。它把"发完等半小时没人接"的事后试错，提前成了事前参考——准确说是"价格预期公示"，不是"报价"。

但它有三个说不通的地方：维度不够，价格本应由规格、距离、时效共同决定，一个数字表达不了；不参与任何计算，既不筛选也不排序，甚至没有和 `reward` 做比较校验；可空，允许以后补填本身就说明业务不依赖它。

最对症的改法是把价格挂到规格上：`runner_item_sizes` 本来就有 `(user_id, item_size)` 复合主键，加一个 `price` 就变成"小件 5 元、中件 8 元、大件 15 元"，选完规格即可算出预估价格，还符合 2NF（价格依赖"这个跑腿 + 这个规格"的组合）。备选方案是用 `base_price` 当起步价、加价规则写进 `remark`，这在真实小生意里很常见，缺点是那句说明是自由文本，机器永远读不了。

答辩时不要把 `base_price` 硬说成报价，直接讲清定价模型：单边定价、无竞价环节、它只是起步价与预期公示、可空且不参与匹配排序。然后主动指出局限和分档报价的改进方向，会很有说服力。

## 7. 做微信小程序是跑在云服务器上的吧，那定时任务的隐患应该没影响？

小程序本身不是云服务器，它只是跑在用户手机上的前端，关掉微信就彻底停了。真正要问的是后端部署在哪：自建云服务器（CVM/ECS）配常驻 Node 进程，`node-cron` 能用；容器平台要设最小实例数 ≥ 1，缩容到 0 就没有进程；云函数没有常驻进程，`node-cron` 完全不会执行，必须改用 `config.json` 里的定时触发器。

"云服务器一直开着"只解决了"机器不关机"，剩下的问题它管不了：PM2 cluster 模式会按 CPU 核数拉起多个进程，每个进程各跑一份 cron，同一个通知会发 N 次，定时逻辑必须抽成单实例进程；每次发布重启都会跳过那几分钟的 tick；服务器默认 UTC，`time_slots` 存的是 `"18:00"` 这种本地时间，不设置 `timezone: 'Asia/Shanghai'` 整个在线计划会偏 8 小时；进程被 OOM 杀掉后靠 PM2 才能拉起；Node 单线程，同步重计算会让 tick 漂移。

文档那句"重启后下一分钟补算"其实是在说这套计算的本质是**幂等的状态同步**，而非事件驱动的定时动作。逻辑不是"18:00 把某人改成上线"，而是"每分钟核算：按 `time_slots` 此刻他应该在线吗？把 `is_online` 同步成该有的值"。所以停机只会产生两段几分钟的窗口——该在线的没出现、该下线还挂着——恢复后立刻自愈，不会丢事件。

你的直觉"影响不大"是对的，但理由要换：不是"服务器不会挂"，而是"就算挂了这套逻辑自己会自愈"。更彻底的做法是彻底不要定时任务，改成查询时实时判断 `time_slots`，代价是 JSON 无法走索引、每个跑腿都要在应用层算一次。现在的方案是把"算"前置成 `UPDATE`、把 `is_online` 当作缓存、用定时任务当刷新器，对"找跑腿高频读、在线状态低频写"这个场景是对的。

## 8. 同一对用户、不同业务有必要分开成多个对话框吗？

有必要，但需要分开的是"对话的业务归属"而非"对话框"——数据库层按业务拆分是唯一可逆的选择，前端是否合并展示随时可改；反过来数据库层合并了将来就拆不开。

会话的边界应当等于关系的边界。微信人与人是社交关系，关系独立存在，所以一人一会话；闲鱼人与物是交易关系，关系依附于"这本《高等数学》"，书卖掉关系就结束。一旦交易关系脱离具体物品，会话就失去参照——同一个人今天问 A、明天问 B、半年后买 C 全混成一条时间线，聊天记录里会出现"这个还在吗""哪个？""就那个蓝色那个"，谁也说不清。

三个实证理由：纠纷追溯需要按 `order_id` 捞出这一单的全部聊天，混在一起就查不出来（`messages.sender_id` 设 `RESTRICT` 正是为此）；上下文展示要求每个会话顶部能挂"高等数学 · ¥15 · 在售"这样的卡片，合并后只能挂最新的；生命周期不同，商品会话随下架结束，代取会话随完成结束，分开才能自然归档。

代价是会碎：同一个卖了很多本书的学长会在消息列表里刷屏。但交易平台的会话本来就多且短命，用户是来办事的不是来社交的，而且有三处低成本缓解——按 `last_time` 倒序、未读置顶；入口从商品/订单详情的"联系 TA"直接进；标题写成"陈晓 · 高等数学"这种人 + 业务的复合形式。还能加一个"按人折叠"视图，按 `(user_a_id, user_b_id)` 分组只显示最新一条，唯一键前两列正好支持，不用动表结构。

反方方案是"一人一会话 + 消息级引用"，在 `messages` 上加 `ref_type`/`ref_id`。它的唯一真优势是连贯性（像微信一样随时接着聊），代价是业务归属只存在于单条消息、历史里没有卡片就查不出来，纠纷追溯要先按人捞全部消息再筛卡片。选择取决于你把这个产品当交易工具还是校园社交，文档选了前者。

还有三个细节值得注意：`biz_type` 只有 `'item'` 和 `'errand'`，没有"无业务"取值，纯社交会话表结构上无法表达，将来要加得先改 ENUM；`biz_id` 无外键，商品被物理删除后会悬空，接口层查不到时应降级显示"商品已下架"；`CHECK (user_a_id < user_b_id)` 把归一化固化在数据库层，比只靠应用层排序严谨——否则后台脚本一插就可能破。

## 9. `runner_id → users.user_id` 写的是 `SET NULL`，可用户明明只禁用不删除，这个动作什么时候才会触发？

这是两套机制，管的是两件事。`users.status = 'disabled'` 是业务层的软删除：用户还在表里，登录被拒，历史订单和聊天都保留，正常流程永远不会走到 `DELETE users`。外键的 `ON DELETE` 动作是数据库层的兜底：只有当有人真的执行 `DELETE FROM users` 时才生效——比如 DBA 清理测试数据、后台脚本误操作、将来做合规性硬删除。平时它不会被触发，但 DDL 必须写清楚"万一删了怎么办"。

`runner_id` 之所以能 `SET NULL`，是因为这一列本来就允许空：订单刚发布时还没人接单，`runner_id IS NULL` 是合法状态；跑腿账号被硬删除后，把接单人清空，订单本身、发布者、金额、状态日志都还在，历史不会整单消失。`publisher_id` 则相反，它是 `NOT NULL`，一张没有发布者的订单没有意义，所以用 `RESTRICT` 直接挡住删除；`messages.sender_id` 也是 `RESTRICT`，聊天记录不能出现"无源消息"；日志表的 `changed_by` 用 `SET NULL`，则是"日志要留、操作人可以丢"。

代价要说清楚：`SET NULL` 保住的是订单，丢的是"谁接的"这条链。真要做纠纷追溯，跑腿的身份就查不回来了。所以这套设计的前提是"正常业务只禁用、不物理删除"；如果将来真允许硬删除，应该先把该用户的相关行归档或匿名化，而不是依赖 `SET NULL` 擦掉关联。答辩时可以一句话概括：软删除是业务策略，外键动作是数据库兜底，两者不矛盾，一个规定正常路径，一个规定异常路径。

## 10. 账号注销后，同一个人是不是就再也不能用原来的学号登录或重新注册了？

在当前这版设计里，是的。注销只是把 `users.status` 改成 `disabled`，行还占着 `student_no` 这个唯一键：登录会在密码校验之后被 `status` 拦下，重新注册又会撞唯一键，所以同一个人既进不去也注册不了新号。这正是"保留行、占用学号"换来的防重注册效果，但副作用是把"后悔"的路也堵死了。

要支持恢复，就得在注销时引入冷静期，而不是立刻把行做成永久壳。可行的一套是：`status` 增加 `deactivated`（或 `pending_deletion`），加 `disabled_at`；冷静期内保留学号和资料，登录时识别到 `deactivated` 就返回"可恢复"，用户验证密码/学号后把状态改回 `active`；超过冷静期再匿名化昵称、手机号、头像，并决定是否释放学号。这里有个容易忽略的结构问题：`student_no` 现在是 `NOT NULL UNIQUE`，真要释放，得允许它为空或写入一个不会与学生号冲突的占位值，唯一键才让得出来。还要和 README 的未来展望对齐：如果注销当下就把昵称、联系方式匿名化，恢复时资料已经回不来；真要做"恢复"，匿名化应推迟到冷静期结束，或者把原资料另存。

复杂度主要在边界而不在表结构：在售商品要自动下架、待接单订单要取消、进行中的订单和聊天要保留、恢复时要不要恢复被匿名化的资料、释放学号后原学号被他人注册怎么办、定时任务按什么频率清理。课程项目可以只做"`status` + `disabled_at` + 冷静期内恢复"，把匿名化和释放学号放到未来展望；答辩时讲清楚"释放学号 = 放弃历史，保留学号 = 保留恢复可能"这个取舍即可。如果既想释放学号又想保留历史，就得在注销时把原学号另存到一张归档表，主表的唯一键才能安全让出。
